What a Hub keeps

Binders Hub is a server a team shares notes, a board and agents through, so unlike the Mac app it holds your work. This page says what it keeps, where that goes and who can read it. The Mac and iPhone apps have their own privacy page. Last updated 1 November 2026.

Who is responsible

A Hub is run by whoever set it up: its operator. The operator decides who may sign in, who its admins are and how its server is kept, and can read what the Hub keeps there, as described below. For anything about the data on a particular Hub, ask its operator.

What a Hub keeps

  • Who you are. Your GitHub login, name and the address of your GitHub picture, from signing in with GitHub, and which binders you’re in.
  • Live work, in Redis. A log of every change in each binder: notes and every edit to them, folders, cards, comments, questions and answers, what agents report as they work, change sets, debriefs, Challenges and chats with agents. Also the Hub’s list of agents, each binder’s members and the Hub’s options.
  • Notes and pictures, on the server’s disk. Notes as Markdown files in a Git repo, committed in batches as you edit, a working copy of each note for editing together, and the pictures added to notes, up to 20 MB each.
  • Keys. The keys of the Hub’s GitHub App and people’s GitHub tokens, sealed with AES-256 under the Hub’s secret. Sign-in, app and agent tokens are kept only as hashes.

Only the keys and GitHub tokens are sealed. The Hub doesn’t encrypt notes, cards or the log, so anyone who can read its Redis or its disk can read them.

Where it goes

  • GitHub. Each binder’s cards are saved as GitHub Issues in the repo it’s linked to, change sets as tracking issues, and debriefs as comments on them. Its notes and their pictures are pushed to that repo too, on a branch of their own, unless the binder is set not to. A personal binder’s notes go to a private binders-notes repo on your own account, once you set that up. The repo’s own visibility decides who else can read these, and GitHub’s terms cover them.
  • Back from GitHub. The Hub reads the issues, pull requests, checks, workflow runs and deployments of its repos, through webhooks or by asking.
  • Agents and whoever runs their models. An agent in a binder can read that binder’s notes and cards over MCP. What it reads goes wherever that agent sends it, usually to the maker of its AI model, such as Anthropic for Claude Code or OpenAI for Codex, under that maker’s terms. The Hub itself calls no AI model: Distill, Challenge and debriefs are done by agents.
  • Other tools. A Mac linked to a binder keeps a copy of it. See what a linked Mac sends, which can include meetings, transcripts, captures and dictations if the person chooses to send them.

The Hub contacts no other outside service. If its operator puts it behind something, such as a Cloudflare tunnel, that service carries its traffic.

Who can read it

  • A binder’s members can read its notes and board, and its owners and admins add and remove people. A Hub’s first binder is open to everyone the Hub lets in until it has a member.
  • A Hub’s admins can open every team binder.
  • A personal binder, at /~login, opens only for you, not for other people or the Hub’s admins. Its notes are not encrypted on the server, though, so whoever can read the server can read them.
  • An agent’s token belongs to the binder it was made in.

Agents and the runner

  • The runner runs on the machine of the person who set the agent up, not on the Hub. It starts Claude Code, Codex or your own command for each card, in a worktree and branch of that card’s own.
  • It reports what the agent does to the card as it goes: the files it read, the commands it ran and what came back. Those reports are kept in the Hub’s log, and anyone in the binder can read them.
  • An agent takes a card only in a repo its owner can push to, and each run gets a token for that one repo that lasts an hour. A Hub with no GitHub App can’t narrow a token, so there the agent uses the machine’s own GitHub login.
  • By default an agent runs with no prompts, so it can reach what its owner’s machine lets it reach. Its owner can change that on the Agents page.
  • A terminal its owner opens on an agent from the web app runs on the runner’s machine. What’s typed and shown in it passes through the Hub while it’s open, and the Hub keeps none of it.
  • An agent’s commits, when they’re made as its owner, carry the owner’s GitHub name and private GitHub email address.

Keeping and deleting

A Hub has no retention period: it keeps what it holds until its operator removes it. Web sessions last 30 days, signing out ends yours, and a token stops working when it’s revoked.

Deleting a note or a card takes it off the board and out of the current notes. It doesn’t erase it: the text stays in the Hub’s log and in the Git history of the notes repo, and any copy already on GitHub stays there. To have something removed for good, ask the Hub’s operator, and remove it from GitHub yourself if it reached there.

Removing someone from a binder ends their access. What they wrote stays.

Cookies, logs and the web app

  • The web app sets only the cookies signing in needs. It has no analytics and loads no scripts or fonts from other companies.
  • Your own browser loads your teammates’ pictures from GitHub. A picture from the web in a note loads straight from the site it’s on, so that site sees your IP address when you open the note.
  • The Hub’s logs record what goes wrong and, if the operator turns it on, each request’s method and path. Anything that looks like a credential is held back. Requests are limited per person or per IP address to slow down abuse.

Asking for access

Access to a Hub is by allow list. Choose Request access anywhere on this site: it opens a message to hello@binders.io with the subject “Binders Hub access request”. Say which GitHub account or organization you want in, and what your team builds. The message goes to the publisher’s inbox through Amazon SES, and the publisher, who runs the Hub, decides who it lets in.

Asking is the only thing the site sends. The pages set no cookie and load nothing from another company.

Contact

Questions about this page: hello@binders.io. If you have found a security problem in the Hub, please write to security@binders.io before making it public, and give us a chance to fix it. Mail to those addresses is delivered through Amazon SES to the publisher’s inbox.
