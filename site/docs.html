Using Binders Hub

Binders Hub is a team server, signed in with GitHub. A note becomes cards, agents do the work, and people approve what ships. Looking for the app on your Mac or iPhone? That's Binders help.

Getting access

How do I get the Hub?

Ask for access: write to hello@binders.io with your GitHub username or organization and what your team builds. There's no sign up yet. A hub lets in only the GitHub accounts and organizations it allows.

Can I install it myself?

Not today. The Hub's code isn't public, so there's nothing for you to download and run, and there's no hosted version to sign up for.

What will my team need?

  • A GitHub account for each person. You sign in with it, and approvals and merges happen as you.
  • Your code on GitHub. Cards are saved as issues in a binder's repo, and agents open pull requests there.
  • For agents, a Mac or Linux machine that has your code and Node 20 or newer, and an agent to run: Claude Code, Codex, your own command, or any tool that speaks MCP.

Signing in

Open your hub's address and choose Sign in with GitHub. If it says you aren't one of the hub's people, ask whoever runs it to add you. If it says no binder has you as a member, ask the binder's owner: owners and admins add people in Settings → Binder.

Next, connect your GitHub from your account page (your picture, top right). A binder's agents and approvals act on your repos through that connection, and the top bar reminds you if it's missing.

What's a binder?

One notebook: its folders and notes, its board, its GitHub repo and its members, at its own address on the hub. Anyone signed in can make one, and owns it. You also get a personal binder at /~yourname, which the app opens to no one else, the hub's admins included.

From a note to a merge

1. Write the note

Write the spec in Notes, together if you like. Agents can join in too: Chat, beside the note, asks one to read it or change it with you.

2. Distill it into cards

Open Distill beside the note, pick an agent and start it. The agent reads the note and proposes work items, each with who it's for, so you need an agent set up first. Accept the items you want and dismiss the rest. Nothing reaches the board until you accept it. New card, on Work, adds a card by hand.

3. Agents take the cards

An agent claims a card from Ready and works on its own branch, in a worktree of its own, never in your checkout. You can watch each step live. When it needs a person it asks, and the card waits in Blocked until you answer.

4. Review the change set

When an agent finishes, its pull request joins a change set, so you review the change as a whole, even when it spans several repos. Close it to new pull requests keeps later work out of it. Two things help you judge it:

  • Debrief: an agent reads the change and sets out what it does, what changed, how it stands against the brief, things to look at and how to try it.
  • Challenge: an agent in a fresh session looks for what's wrong, from the diff, the brief and the done-when alone. It doesn't see the author's plan or log. The hub prefers an agent that didn't write the change, or you can pick one. Its findings come worst first, with the change's blast radius: what the change touched and where that's still used. That's found by name, so treat it as a first look and not a proof. You can then ask the author to reply to each finding, for one round.

5. Approve and merge

The button says how many, such as Approve 3 and merge. It approves the set's pull requests as you and merges them in order, each once its checks pass. If a check fails, nothing merges until it passes. If a pull request conflicts with its base, the hub settles what it can, and changes to the same lines go back to the agent.

6. Follow it to production

Delivery shows each environment and what's running there, from your GitHub Actions runs and deployments. An environment that needs approval waits for someone to press Promote.

Agents

How do I set up an agent?

In Agents, choose Set up an agent. It gets a token, shown once, and the settings to paste into Claude Code, Codex, Claude Desktop or another MCP client. Anyone with the token can act as that agent, so keep it where the agent runs. New token replaces it, and Revoke stops it at once.

How do I keep one taking cards?

An agent on its own only calls the hub while it's working on something you asked. The runner keeps it listening, and starts it for each card on the machine where your code is. Start the runner, on the Agents page, gives you a one-line install with the token filled in. Then:

binders list            # every agent on this machine, and how it's doing
binders logs NAME -f    # what it's doing
binders restart NAME    # also stop, start, remove; --all for every one

It runs as a service of yours (a LaunchAgent on a Mac, a systemd --user unit on Linux), starts at login and restarts after a crash. Sign in to your tools, such as Claude Code or Codex, beforehand: a background service can't show their sign-in.

An agent that says nothing for 15 minutes is stopped as stuck, and its card says so. The time limit, model and tool are in its settings on the Agents page.

How much can an agent do on my machine?

That's the agent's access setting. Full access, the default, runs with no prompts. Auto, for Claude Code only, lets it decide what's safe. Edits only lets the tool edit files without asking, and what else it can do depends on the tool. The runner reads this before each card. With full access, a worktree keeps the work away from your checkout, but it isn't a sandbox: the tool can do whatever your account can on that machine.

How much of GitHub can an agent reach?

No more than the person who set it up. An agent takes a card only in a repo its owner can push to, and each run gets a token for that one repo, lasting an hour and renewed on long runs. The machine's own GitHub login isn't used, unless the hub has no GitHub App: then tokens can't be narrowed, the agent uses that login, and the runner's log says so.

With the Mac app

Can I use a hub from Binders for Mac?

Yes, with Binders 0.14.0 or later. Settings → Team signs your Mac in to a hub, in your browser. Link to Hub…, in a binder's menu, makes a new binder on the hub or joins one you're in. Its notes, folders, pictures and cards then stay the same on your Mac and on the hub, both ways, offline too. A linked binder's board, Distill and agents are the hub's.

What stays on my Mac?

Your Mac keeps what you heard, and the hub gets what you choose to share. A linked binder's meetings, captures, knowledge and dictations stay on your Mac until you send them with Send to Hub…, or send a meeting as a note. Sent, they're notes on the hub that its members can read. Notes made from what you said to yourself never go up with the binder.

The promises in Binders' privacy notes are about the app on your Mac and iPhone. What you share with a hub is kept as described below.

Where your work is kept

What does a hub hold?

  • On GitHub, in the binder's repo: cards, as issues; notes, as Markdown on a branch of their own; and your code and pull requests. Settings → Binder can turn off pushing notes.
  • On the hub's server: a Git copy of the notes, live work in Redis, such as each change to the board and agents' reports, and the keys it needs for GitHub, sealed with the hub's secret.

So a binder's cards and notes are still in its repo if you stop using Binders. What's only on the hub's server is whoever runs that hub's to look after.

Where does my code go when an agent works?

Agents run on your machines, with your tools. What they read goes wherever that tool sends it, usually to whoever runs its model. Each step an agent reports appears on its card, where the binder's members can see it.

Something else?

Write to hello@binders.io. For a security problem, please write to security@binders.io before making it public.
