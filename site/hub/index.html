The pipeline

One line from the spec to what's deployed.

  1. NoteThe spec, written together in Markdown.
  2. DistillProposes the work, quoting the note.
  3. CardsAccepted work, each saved as a GitHub Issue.
  4. AgentsClaim cards and report each step.
  5. Pull requestsOne branch and worktree for each card.
  6. Change setRelated pull requests, approved as one.
  7. CI/CDChecks and environments, on each change.

Start from the spec

Notes become work when someone says so.

Write a note together. Distill reads it and proposes work items, each with the note's exact words it came from. Nothing reaches the board until someone accepts it.

A card an agent suggests on its own waits as proposed too, until a person moves it on.

Agents work in the open

Watch the work, and answer when it's stuck.

Agents connect over MCP, claim a card, report each step live, and ask when they're stuck. A person's answer starts them again on that card.

The runner keeps an agent taking cards on the machine where the code is. It starts Claude Code, Codex or your own command, and works each card in its own worktree and branch, never in your checkout. Any other MCP client can connect too, without the runner's worktrees.

Change sets

Review the change, not twenty pull requests.

A change set brings related pull requests together, across repos, with one approval. They merge in the order you set, each as soon as it's ready. One that isn't ready waits and says why, and the others don't stop for it.

A failed check refuses the approval, and the repo's own rules still apply on GitHub.

Debrief gives you an agent's written account of what the change proposes. A card's debrief is kept as a comment on its issue.

Challenge

Reviewers who don't take the author's word for it.

Ask for a Challenge and a reviewer agent judges the code without seeing the author's plan or log. It gets the diff, the brief and the card's “done when”, in a checkout of its own, with no earlier session.

Each finding has a file and line, a severity and a confidence. It also gets the change's blast radius: what the change touched, its uses elsewhere that the change didn't, and the tests that mention it. The blast radius is found by name, so it's a first look and not a proof.

You can pick the reviewer. Left to the Hub, an agent that didn't write the work comes first.

For the lead who approves it

Three questions, answered plainly.

What can an agent reach?

Which reposAn agent takes a card only in a repo its owner can push to, as GitHub says with the owner's own sign-in. Otherwise it's refused, and told why. A hub that doesn't sign people in with GitHub has no owner to ask, so it doesn't make this check.
GitHub, by defaultIt commits and pushes as its owner, with the owner's GitHub sign-in to the Hub. It can reach what that sign-in can, and commits carry the owner's name.
GitHub, as the appSet an agent to commit as the Hub's GitHub App, and each run gets a token for one repo that lasts an hour, renewed on long runs.
The machine's GitHub loginA hub with no GitHub App can't narrow a token, and one token can't cover a folder of several repos. In those cases the agent uses the machine's own GitHub login, and the runner's log says so.
The machineAgents run on a machine you choose. Each agent's access is set in the Agents page: full, with no prompts, which is the default; Auto, where Claude Code decides what's safe; or edits only. Not every tool offers all three.

Who reviewed the work?

A person, by name. Only someone signed in can approve a change set, the Hub records who did, and agents get no tool for it. Pull requests ready at that moment are approved and merged on GitHub as that person. Any that become ready later are merged by the Hub's GitHub App. GitHub won't let you approve your own pull request, so if an agent pushed as you and you approve the set, it merges without a GitHub approval, unless the repo's rules require one.

Where is it deployed?

Delivery shows each environment, the version on it and the change sets that version carries. Checks, workflow runs and deployments come from GitHub, on each change. An environment that needs approval waits for a person, who promotes it in the app. That runs your GitHub workflow, if the environment has one. A card goes live when it reaches the last environment.

Your work stays in your tools

Switch Binders off, and your work is still in GitHub.

In GitHub and Git

  • Cards, as GitHub Issues, with the Hub's fields in a hidden block in the body
  • Debriefs, as comments on those issues
  • Notes, as Markdown files in a Git repo
  • Pull requests, checks, workflow runs and deployments

On the Hub

  • Live work, in Redis
  • Change sets, and agents and their settings
  • Challenge findings, unless a binder posts them as a review on the pull request
  • GitHub keys and sign-ins, sealed

Self-hosting

It runs on one server.

The Hub is built to run with Docker Compose: the Hub, its Redis, and an optional Cloudflare tunnel for its public address. Its repository is private today, so this isn't something you can set up on your own yet.

The private half

Your Mac keeps what you heard. The Hub gets what you chose to share.

Binders for Mac is its own product, and its privacy promise is its own. Notes in a binder you link to a Hub are shared there. Meetings, captures and dictations stay on your Mac unless you choose Send to Hub.
